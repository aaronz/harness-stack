# AI-Ready Evaluator 详细功能规格

## 1. 需求评估引擎

### 1.1 功能概述

需求评估引擎是系统的核心模块，负责对输入的需求文本进行AI就绪度评估。引擎基于五大维度（上下文完备性、逻辑原子性、边界明确性、可验证性、技术约束清晰度）对需求进行分析，生成综合评分和详细的评估报告。

### 1.2 功能需求

#### 1.2.1 需求解析与预处理

系统需要支持多种输入格式：纯文本输入（用户直接粘贴需求文本）、Markdown格式输入、JSON格式输入（支持结构化需求数据）。输入的需求文本需要进行预处理，包括去除多余空白字符、标准化标点符号、识别并标记关键实体（业务术语、技术名词、数据实体等）。系统需要检测输入需求的语言，支持中文和英文双语评估。

#### 1.2.2 多维度评估

系统需要对需求的五大维度进行全面评估：

**上下文完备性评估（权重25%）**：

- 业务目标陈述检查：评估需求是否清晰描述了业务问题而非技术方案
- 术语定义完整性检查：评估领域特定术语是否有明确定义
- 用户旅程映射检查：评估功能在用户操作流程中的位置是否明确
- 数据实体关系检查：评估涉及的数据对象及其关系是否清晰

**逻辑原子性评估（权重25%）**：

- 功能单一性检查：评估需求是否只做一件事（符合SRP原则）
- 上下文窗口适配检查：评估需求描述长度是否在AI有效上下文窗口内（建议小于3000 tokens）
- 依赖显式化检查：评估前置条件、外部服务依赖、数据依赖是否明确列出
- 原子性验证：评估需求能否独立开发、独立测试、独立部署

**边界明确性评估（权重20%）**：

- 输入域定义检查：评估每个输入参数的合法值域、非法值域、空值处理是否明确
- 状态转换完整性检查：评估所有可能的状态及转换条件是否完整（非仅Happy Path）
- 并发与竞态检查：评估是否涉及并发访问，资源竞争如何处理
- 性能边界检查：评估时间复杂度、空间复杂度、吞吐量要求是否明确

**可验证性评估（权重15%）**：

- 示例驱动检查：评估是否提供输入/输出示例（包括边界示例、异常示例）
- 验收标准量化检查：评估是否有非模糊的量化指标
- 可自动化测试检查：评估验收标准能否转化为单元测试断言
- 行为契约检查：评估接口的前置条件、后置条件、不变式是否明确

**技术约束清晰度评估（权重15%）**：

- 架构合规性检查：评估必须使用的架构模式是否明确
- 技术栈锁定检查：评估编程语言版本、框架版本、库白名单/黑名单是否明确
- 接口契约检查：评估API协议、数据格式是否明确
- 安全约束检查：评估身份认证方式、权限模型、敏感数据处理规则是否明确

#### 1.2.3 综合评分计算

评分算法采用加权评分结合复杂度惩罚机制：

```
AI就绪分 = Σ(维度得分 × 维度权重) × 复杂度惩罚系数

复杂度惩罚系数：
- 简单需求（CRUD类）：1.0
- 中等需求（业务逻辑类）：0.9
- 复杂需求（算法/架构类）：0.7
```

AI就绪等级划分：

- S级（90-100分）：AI可独立完成，无需人工干预
- A级（75-89分）：AI可实现，但需人工Review关键边界
- B级（60-74分）：AI生成代码后需人工大幅修改
- C级（<60分）：不建议AI实现，风险过高

#### 1.2.4 批量评估功能

系统需要支持批量评估功能，用户可以一次性提交多个需求（最多50个）进行批量分析。批量评估需要显示整体进度和单个需求的完成状态。批量评估结果支持导出为CSV或JSON格式。

#### 1.2.5 增量评估功能

系统需要支持增量评估功能，当需求文档更新后可以快速重新评估。增量评估需要对比前后版本的评估结果差异，高亮显示发生变化的部分。增量评估支持版本历史管理，用户可以查看任意历史版本的评估结果。

### 1.3 数据模型

#### 1.3.1 评估请求

```
interface EvaluationRequest {
  id: string;
  requirementText: string;
  requirementFormat: 'text' | 'markdown' | 'json';
  complexity: 'simple' | 'medium' | 'complex';
  metadata: {
    submittedAt: Date;
    submitter: string;
    tags: string[];
  };
}
```

#### 1.3.2 评估结果

```
interface EvaluationResult {
  requestId: string;
  overallScore: number;
  level: 'S' | 'A' | 'B' | 'C';
  dimensionScores: {
    contextSufficiency: number;
    atomicity: number;
    boundaryDefiniteness: number;
    verifiability: number;
    technicalConstraints: number;
  };
  riskHeatmap: RiskHighlight[];
  contextGaps: string[];
  recommendations: Recommendation[];
  evaluatedAt: Date;
}
```

### 1.4 接口设计

#### 1.4.1 评估接口

```
POST /api/v1/evaluations
Request Body: {
  requirementText: string,
  format?: 'text' | 'markdown' | 'json',
  complexity?: 'simple' | 'medium' | 'complex'
}
Response: {
  id: string,
  status: 'processing' | 'completed' | 'failed',
  result?: EvaluationResult
}
```

#### 1.4.2 批量评估接口

```
POST /api/v1/evaluations/batch
Request Body: {
  requirements: Array<{
    text: string,
    format?: string,
    complexity?: string
  }>
}
Response: {
  batchId: string,
  total: number,
  completed: number,
  results: EvaluationResult[]
}
```

#### 1.4.3 结果查询接口

```
GET /api/v1/evaluations/:id
Response: EvaluationResult
```

## 2. LLM集成层

### 2.1 功能概述

LLM集成层负责管理系统与各种LLM提供商的连接和交互，支持运行时动态切换LLM提供商，允许用户根据成本、效果和合规需求灵活选择AI模型。

### 2.2 功能需求

#### 2.2.1 多提供商支持

系统需要支持以下LLM提供商：

- OpenAI API（GPT-4o、GPT-4o-mini）
- Anthropic API（Claude 3.5、Claude 3.0）
- Google Gemini API
- 本地模型（Ollama、LM Studio）

每个提供商需要实现统一的接口适配层，确保核心评估逻辑与具体LLM实现解耦。

#### 2.2.2 动态切换机制

系统需要支持运行时动态切换LLM提供商。切换操作不需要重启服务，即时生效。切换时需要确保进行中的评估任务不受影响。系统需要记录每次LLM切换的历史，便于问题追溯。

#### 2.2.3 智能路由

系统需要实现智能路由机制，根据需求复杂度选择合适的LLM模型：

- 简单需求（CRUD类）：使用轻量模型（如GPT-4o-mini、Claude-haiku）
- 中等需求（业务逻辑类）：使用中等模型（如GPT-4o、Claude-sonnet）
- 复杂需求（算法/架构类）：使用强模型（如GPT-4o、Claude-opus）

智能路由规则可由用户自定义配置。

#### 2.2.4 容错机制

系统需要实现完善的容错机制：当主选LLM调用失败时，自动切换到备用LLM；当所有LLM都不可用时，返回评估失败并提示用户稍后重试；实现请求重试机制，重试次数和间隔可配置；实现调用超时控制，避免长时间阻塞。

#### 2.2.5 本地部署支持

系统需要支持本地模型部署（Ollama/LM Studio），满足数据隐私要求。本地模型需要支持热更新，无需重启服务。本地模型需要实现健康检查，确保模型可用。

### 2.3 配置管理

#### 2.3.1 API密钥管理

系统需要安全存储LLM提供商的API密钥，禁止明文保存。API密钥支持轮换更新，无需中断服务。API密钥支持环境变量配置，便于容器化部署。

#### 2.3.2 提供商配置

```
interface LLMProviderConfig {
  provider: 'openai' | 'anthropic' | 'google' | 'local';
  model: string;
  endpoint?: string;
  apiKey: string;
  maxTokens: number;
  temperature: number;
  timeout: number;
  priority: number;
  enabled: boolean;
}
```

## 3. 评估报告生成器

### 3.1 功能概述

评估报告生成器负责将评估结果以可视化的方式呈现给用户，包括AI就绪等级、各维度得分、风险热力图、优化建议等内容。

### 3.2 功能需求

#### 3.2.1 评分报告展示

系统需要展示完整的评分报告，包括：总体得分和AI就绪等级（S/A/B/C级）；五大维度的详细得分和权重分布雷达图；得分趋势变化图（与历史评估对比）；等级分布统计（批量评估场景）。

#### 3.2.2 风险热力图

系统需要生成风险热力图，高亮显示需求原文中AI最可能误解的段落。风险热力图需要支持点击查看详细解释。风险热力图的颜色梯度：红色表示高风险（AI极可能误解）、黄色表示中风险（AI可能误解）、绿色表示低风险（AI可正确理解）。

#### 3.2.3 上下文缺口分析

系统需要列出AI生成代码时必定缺失的外部知识。上下文缺口需要分类展示（业务背景缺失、术语定义缺失、数据关系缺失、技术约束缺失）。每个缺口需要提供具体的改进建议。

#### 3.2.4 报告导出

系统需要支持多种导出格式：Web端在线查看（默认）、PDF导出（包含完整报告内容和样式）、JSON导出（便于程序化处理）、CSV导出（适合数据分析和对比）。

#### 3.2.5 历史版本对比

系统需要支持历史版本对比功能。用户可以查看任意历史版本的评估结果。对比视图需要高亮显示发生变化的部分。对比视图需要展示变化前后的得分差异。

## 4. 优化建议引擎

### 4.1 功能概述

优化建议引擎基于评估结果生成针对性的需求优化建议，帮助需求方完善需求描述以提升AI实现成功率。

### 4.2 功能需求

#### 4.2.1 建议生成

优化建议引擎需要生成以下四类建议：

**上下文增强类**：

- 补充用户旅程图，说明此功能在整体流程中的位置
- 定义关键业务术语的含义（如「有效订单」的业务定义）
- 补充数据实体关系图，说明对象之间的关联

**边界完备类**：

- 补充当库存为0时的系统行为
- 明确并发场景：是否允许同一用户同时提交多个请求
- 补充异常流程处理说明

**原子化建议类**：

- 建议拆分为两个需求：数据获取逻辑与展示逻辑
- 依赖服务接口契约未明确，建议补充或Mock定义
- 建议明确前置条件和后置条件

**可验证性增强类**：

- 建议补充3个边界测试用例：空输入、超大输入、特殊字符输入
- 建议定义性能基准：接口响应时间P99<500ms
- 建议补充输入输出示例

#### 4.2.2 建议优先级

优化建议需要按优先级排序：高优先级（直接影响AI实现成功率的建议）、中优先级（可能影响AI实现质量的建议）、低优先级（建议性改进，不影响基本功能）。

#### 4.2.3 建议可操作性

每条建议需要明确指出：问题所在（哪个维度、哪个检查点存在问题）、具体改进方向（应该如何修改需求描述）、修改示例（展示修改前后的对比）。建议需要避免空洞的通用描述，必须具有可操作性。

## 5. 配置管理中心

### 5.1 功能概述

配置管理中心允许用户管理系统运行的各种配置参数，包括LLM配置、评估参数、系统设置等。

### 5.2 功能需求

#### 5.2.1 LLM配置管理

用户可以管理LLM提供商的配置，包括：添加/删除LLM提供商、配置API密钥和端点、选择默认模型、调整模型参数（temperature、maxTokens等）。

#### 5.2.2 评估参数配置

用户可以调整评估相关的参数，包括：五大维度的权重分配（默认权重：25%、25%、20%、15%、15%）、复杂度惩罚系数（默认：1.0、0.9、0.7）、评分阈值配置（定义S/A/B/C级的分数边界）、复杂度自动检测规则。

#### 5.2.3 系统配置

用户可以管理系统级别的配置，包括：系统主题和界面定制、报告导出格式默认设置、评估历史保留策略、系统通知配置。

#### 5.2.4 配置导入导出

配置支持导入导出，便于在不同环境间迁移配置。导出格式为JSON，导入时需要校验配置合法性。配置变更需要记录操作日志，支持审计追溯。

## 6. 用户管理

### 6.1 功能概述

系统需要提供基础的用户管理功能，支持多租户隔离和数据安全管理。

### 6.2 功能需求

#### 6.2.1 用户认证

系统需要支持用户注册和登录。认证方式支持：邮箱/密码登录、OAuth第三方登录（GitHub、Google）。登录会话需要实现JWT token机制，支持token刷新。

#### 6.2.2 权限管理

系统需要实现基于角色的权限控制：

- 管理员：全部权限，包括系统配置、用户管理
- 普通用户：评估功能、报告查看、配置个人设置
- 访客：只读评估报告

#### 6.2.3 多租户支持

系统需要支持多租户隔离。不同租户之间的数据完全隔离。租户可以自定义配置，不影响其他租户。
