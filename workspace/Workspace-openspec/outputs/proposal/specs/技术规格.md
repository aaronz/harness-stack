# AI-Ready Evaluator 技术规格

## 1. 技术架构

### 1.1 整体架构

系统采用前后端分离的微服务架构，前端使用Next.js 14 + TypeScript 5，后端使用Node.js + Express + TypeScript。数据库采用SQLite文件型数据库，通过Prisma ORM进行数据访问。整个技术栈选择遵循轻量极简原则，降低运维成本。

整体架构分为四层：接入层负责处理用户请求的路由和认证；应用层负责业务逻辑的处理和协调；领域层负责核心评估逻辑的实现；基础设施层负责数据持久化、LLM集成和外部服务调用。

前后端之间通过RESTful API进行通信，使用JWT进行身份认证。前端采用Server-Side Rendering (SSR)架构，利用Next.js的静态生成和服务端渲染能力优化首屏加载性能。

### 1.2 技术栈详情

前端技术栈包括：Next.js 14作为React框架，TypeScript 5作为编程语言，Tailwind CSS作为样式框架，Zustand作为状态管理库，React Query作为服务端状态管理，Recharts作为图表可视化库。开发环境使用ESLint和Prettier进行代码规范检查。

后端技术栈包括：Node.js作为运行时环境，Express作为Web框架，TypeScript作为编程语言，Prisma作为ORM工具，SQLite作为数据库，jsonwebtoken作为JWT认证库，axios作为HTTP客户端。部署环境支持Docker容器化。

### 1.3 模块划分

系统模块划分如下：

**前端模块**：

- 评估页面模块：负责需求输入、评估发起、结果展示
- 报告模块：负责评估报告的查看、导出、对比
- 配置模块：负责系统配置、LLM管理
- 用户模块：负责用户认证、个人中心

**后端模块**：

- 评估引擎模块：负责需求评估的核心逻辑
- LLM适配模块：负责与各LLM提供商的集成
- 报告生成模块：负责评估报告的生成和导出
- 用户认证模块：负责用户注册、登录、权限管理
- 配置管理模块：负责系统配置的存取

## 2. 数据库设计

### 2.1 数据模型

系统使用SQLite作为数据存储，通过Prisma ORM进行数据访问。主要数据模型包括：用户（User）、评估任务（Evaluation）、评估结果（EvaluationResult）、LLM配置（LLMProvider）、系统配置（SystemConfig）。

### 2.2 表结构

#### 2.2.1 用户表（User）

```
model User {
  id            String   @id @default(uuid())
  email         String   @unique
  password      String
  name          String?
  role          Role     @default(USER)
  tenantId      String?
  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt

  evaluations   Evaluation[]
}
```

#### 2.2.2 评估任务表（Evaluation）

```
model Evaluation {
  id              String   @id @default(uuid())
  userId          String
  requirementText String
  requirementFormat String @default("text")
  complexity      Complexity @default(MEDIUM)
  status          EvaluationStatus @default(PENDING)
  
  result          EvaluationResult?
  
  createdAt       DateTime @default(now())
  updatedAt       DateTime @updatedAt
  
  user            User     @relation(fields: [userId], references: [id])
}
```

#### 2.2.3 评估结果表（EvaluationResult）

```
model EvaluationResult {
  id                  String   @id @default(uuid())
  evaluationId        String   @unique
  
  overallScore        Float
  level               EvaluationLevel
  
  contextSufficiency  Float
  atomicity           Float
  boundaryDefiniteness Float
  verifiability       Float
  technicalConstraints Float
  
  riskHeatmap         Json
  contextGaps         String[]
  recommendations     Json
  
  evaluatedAt         DateTime @default(now())
  
  evaluation          Evaluation @relation(fields: [evaluationId], references: [id])
}
```

#### 2.2.4 LLM提供商配置表（LLMProvider）

```
model LLMProvider {
  id          String   @id @default(uuid())
  name        String
  provider    ProviderType
  model       String
  endpoint    String?
  apiKey      String
  maxTokens   Int      @default(4096)
  temperature Float    @default(0.7)
  timeout     Int      @default(30000)
  priority    Int      @default(1)
  enabled     Boolean  @default(true)
  
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt
}
```

#### 2.2.5 系统配置表（SystemConfig）

```
model SystemConfig {
  id        String   @id @default(uuid())
  key       String   @unique
  value     Json
  updatedAt DateTime @updatedAt
}
```

## 4. 评估引擎算法

### 4.1 评估流程

评估引擎的工作流程分为五个阶段：

**第一阶段：需求解析**

- 解析输入的需求文本，提取关键信息
- 识别需求格式（纯文本、Markdown、JSON）
- 估算需求复杂度等级

**第二阶段：维度评估**

- 对每个评估维度进行独立评估
- 每个维度内部包含多个检查点
- 计算每个检查点的得分

**第三阶段：LLM辅助评估**

- 将需求文本和检查点清单发送给LLM
- LLM返回每个检查点的评估结果
- 解析LLM返回结果，转换为结构化数据

**第四阶段：综合计算**

- 根据权重计算加权得分
- 应用复杂度惩罚系数
- 确定AI就绪等级

**第五阶段：报告生成**

- 生成风险热力图
- 识别上下文缺口
- 生成优化建议

### 4.2 评分算法

评分算法核心公式：

```
维度得分 = Σ(检查点得分 × 检查点权重) / Σ(检查点权重)

AI就绪分 = Σ(维度得分 × 维度权重) × 复杂度惩罚系数

复杂度惩罚系数：
- simple: 1.0
- medium: 0.9
- complex: 0.7
```

检查点评估采用规则匹配和LLM判断相结合的方式。规则匹配用于检测明确的问题（如缺少技术栈定义、缺少输入输出示例等），LLM判断用于评估模糊的质量问题（如业务目标描述是否清晰、需求颗粒度是否合适等）。

### 4.3 复杂度自动检测

系统支持自动检测需求复杂度：

**简单需求（CRUD类）特征**：

- 单个资源的基本操作（增删改查）
- 明确的输入输出定义
- 无复杂业务逻辑

**中等需求（业务逻辑类）特征**：

- 涉及多个资源或服务
- 有条件分支和状态转换
- 有业务规则约束

**复杂需求（算法/架构类）特征**：

- 涉及算法设计或架构规划
- 有性能要求或约束
- 涉及多个系统集成

## 5. 安全设计

### 5.1 认证与授权

系统采用JWT进行身份认证。Access Token有效期为1小时，Refresh Token有效期为7天。用户密码使用bcrypt进行哈希存储，禁止明文保存。

权限控制采用RBAC模型：

- 管理员：系统配置、用户管理、评估管理
- 普通用户：个人评估、报告查看、个人配置
- 访客：只读报告

### 5.2 数据安全

敏感数据（如API密钥）使用AES-256加密存储。数据传输使用HTTPS加密。用户数据支持逻辑删除，物理数据保留30天后自动清理。

### 5.3 API安全

API接口实施_RATE Limiting：每个用户每分钟最多60次请求。关键接口实施请求验证和参数校验。LLM调用实施超时控制和异常处理。

## 7. 部署架构

### 7.1 容器化部署

系统使用Docker进行容器化部署：

```dockerfile
# 后端Dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
EXPOSE 3000
CMD ["npm", "start"]

# 前端Dockerfile
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:alpine
COPY --from=builder /app/.next /usr/share/nginx/html
COPY nginx.conf /etc/nginx/nginx.conf
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```
